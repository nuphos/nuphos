# Subscribe to Task completion over MCP

After `nuphos_ask(wait: false)` returns a `session_id`, open `GET /mcp?session_id=<id>` with the same `Authorization: Bearer ...` header. The server returns `text/event-stream`; each `message` event contains a JSON-RPC `notifications/nuphos/session` notification. A caller that wants completion notifications keeps this stream open instead of polling `nuphos_check`.

Notification `params` contain the session ID, status, message count, and any saved answer, error, pending questions or latest durable `task_report`. `status: completed` has the same meaning as `nuphos_check`: a saved answer with no active run or pending input. It means that turn finished, not that every objective is verified. For delegated Tasks, `task_report.status: done` is the agent's explicit report that the Task completed; `ready`, `waiting`, `blocked` and `failed` remain distinct. A report can arrive while a turn is still running.

The first connection returns the current state even if the answer or report was saved before subscription. Each changed state gets a stable SSE `id`. Save it and send it as `Last-Event-ID` on reconnect; an unchanged state is not sent again. Reconnects rebuild current state from the existing database and run state, so reconnecting to another backend or after a restart does not depend on an old callback. Delivery is at least once: deduplicate by ID. Intermediate states during a disconnect can coalesce into the latest state; this is not an event-history log or an exactly-once webhook queue.

The server sends keepalive comments and `retry: 1000`, and rotates connections after about 55 seconds so authentication is checked again. Reconnect after EOF or a retryable transport failure using the current token and last event ID. A revoked or expired token must be refreshed through the usual authentication flow. Access is checked throughout the connection; revoked session access closes it with `notifications/nuphos/subscription_closed` and `reason: access_revoked`. Missing/private sessions are indistinguishable and return 404 before streaming. Invalid cursors return 400. Generic GET requests without a session ID keep returning 405, so MCP clients probing the optional transport retain the existing behavior. Unauthenticated requests return the same MCP OAuth challenge as POST.

Each user may hold up to three subscriptions across their sessions and tokens. With Redis configured, this limit is shared by backend replicas; without Redis it applies per backend process. An excess connection receives HTTP 429 with `Retry-After: 5`. If Redis coordination is unavailable, the server returns HTTP 503 with the same retry guidance. Disconnecting or rotating a stream releases its slot; a reservation left by a failed process expires automatically.

This adds no notification store, callback URL, background worker or outbound request. Existing `report_task` delivery to a parent continues independently. Download evidence with the file-transfer tools; transcript and event catch-up remain available through `nuphos_check` and `nuphos_events`.
